# 页面设计原则：同一对象，不同身份

用户与管理员面对同一类业务（线路、媒体账号、商店、求片、积分）时，页面是合并还是拆开？本页给出判定规则，新增模块一律按此执行。

## 判定规则：按“对象范围 × 任务”拆，不按角色拆

| 问题 | 是 → | 否 → |
|---|---|---|
| 两种身份操作的是**同一个对象、同一份数据**，只差能不能改？ | **同一页面**，写操作按权限点显示或隐藏（“仅查看”） | 继续下一题 |
| 一方只处理**自己的**数据（我的…），另一方处理**所有人的**数据或系统配置？ | **拆成两页**：个人区“我的…”，管理区“…管理” | 继续下一题 |
| 任务性质不同：**使用**（选择、兑换、查看结果）与**配置**（增删改、规则、对账）？ | **拆成两页** | 同一页面 |

表面上的重复（用户“线路”页与管理员“推流节点与线路”页都出现线路）并不是冗余：前者的对象是“我选哪条”，后者的对象是“系统有哪些线路、怎么组成”。对象、数据量、操作密度都不同，硬合并会让普通用户页背上管理控件，也会让管理页被“选择”这种单对象交互限制。

## 本项目的归类

| 业务 | 用户侧（个人区） | 管理侧（管理区） | 结论 |
|---|---|---|---|
| 线路 | `/lines` 选择自己的线路 | `/admin/stream` 节点与线路配置 | 拆分；共享延迟徽标等展示组件 |
| 媒体账号 | `/my-media` 自己的账号、续期、改密 | `/admin/media-accounts` 全部账号的检索与处置 | 拆分；管理员自己的账号仍在 `/my-media` |
| 求片 | `/wishes` 我的求片与额度 | `/admin/wishes` 处理队列 | 拆分 |
| 商店 | `/shop` 购买与我的礼品卡 | `/admin/shop` 商品与礼品卡 | 拆分 |
| 积分 | `/points` 余额、签到、红包 | `/admin/points` 积分对账 | 拆分 |
| 个人资料 | `/profile` | `/user` 用户管理 | 拆分；管理页的详情抽屉复用资料页的展示组件 |
| 服务器列表 | — | `/admin/media-servers` | 仅管理 |
| 媒体账号“只读详情” | 同一组件，管理员多出处置按钮 | 同左 | **同一组件**，按权限点差异化 |

## 避免冗余的做法

1. **共享组件，不共享页面**：徽标、卡片、空状态、表单片段放在 `components/`，两个页面各自组合。
2. **不做互链入口**:用户页与管理页各自独立进入,不在页头互放“管理 / 以用户视角查看”之类的跳转。
3. **管理员也是用户**：管理员保留个人区全部入口，个人页永远是“我的”视角，不混入管理控件。
4. **同对象同页**：只差读写权限时（例如系统设置的只读与可写），用“仅查看”呈现，不另开页面。
5. **锁定而非隐藏**：普通用户看不到的付费权益，用一张带锁的提示卡说明，不展示管理侧概念（节点、匹配规则）。
6. **后端为准**：页面从不在前端复制“角色 × 层级”规则；可见集合由后端返回，前端只做展示。

## 业界参照

- **Stripe / GitHub / Vercel**：账户设置（我的）与组织或项目管理（所有人的）分属不同导航层级，同一个资源在两处出现，但对象与操作密度不同。
- **Linear / Notion**：同一页面按权限切换可编辑状态（“仅查看”），而不是为只读者另做一页。
- **AWS / GCP 控制台**：使用面（“我的实例”）与管理面（IAM、配额、计费）分开，使用面与管理面分开。
