# EMS 产品需求文档（草案）

<span class="badge-p1">DRAFT</span> 版本 0.1 · 2026-10-12 · 本文档描述 **Web 前端的功能模块、展示方式与交互逻辑**，不是 UI 视觉设计稿。

## 产品是什么

EMS v2 是自托管的 **Emby 媒体账号运营平台**：围绕“媒体账号”提供积分经济（签到、红包、商店）、邀请树治理、求片工单、推流线路与节点、Telegram Bot 通知，以及面向管理员的配置与运维能力。

## 文档目的与边界

| 范围内 | 范围外 |
|---|---|
| 功能模块与子功能清单 | 视觉稿、配色、组件样式 |
| 每个功能“怎么展示、怎么交互” | 后端实现细节（见后端 OpenAPI 契约） |

## 实现状态说明

- <span class="badge-built">已实现</span>：前端页面与后端接口均已存在，本文档按现状描述并标出差距。
- <span class="badge-planned">待实现</span>：后端接口在契约中标记为 `planned`，或前端页面尚不存在；本文档给出目标行为。
- 原始设计（`Backup/ems/docs`）在实现中已有调整；冲突处以当前仓库的角色矩阵与功能清单为准，并记录在 [决策记录](/decisions)。

## 全局产品原则

1. **前端不含业务规则**：权限、能力、特性开关、可选线路、求片额度全部由后端下发，前端只渲染。
2. **对用户无感优先**：只有一条线路时不显示选择器；节点路由对用户完全透明。
3. **两级禁用**：仅“管理员禁用用户”会阻断登录；媒体账号到期、停用、清除只禁用 Emby 相关操作，**续期入口始终可用**，保证用户可自救。
4. **危险操作需确认**：展示影响范围，必要时二次验证；最终以后端为准。
5. **溯源即信任**：积分、红包、兑换码、邀请关系都能回答“谁、何时、做了什么”。

## 涉及的角色

`user`（层级 normal / vip / whitelist）、`admin`、`super_admin`。详见 [角色、层级与权限](/roles-permissions)。
